The central idea

Measure growth, not seconds

Wall-clock time is useful for benchmarking one implementation, but it depends on the computer, language, compiler, and current system load. Algorithm analysis asks a more portable question: how does the amount of work change when the input gets larger?

Suppose we search for a name in a list

If we scan from the beginning, a list that is twice as long may require roughly twice as many checks. Nanoseconds differ across machines; the rule “work grows in proportion to list length” does not.

Step 3

Keep the growth pattern

Exact operation counts are often messy. Asymptotic notation keeps the part that determines growth for large n and ignores constant factors and lower-order terms.

Suppose an algorithm performs

Linear growth

If n doubles, the dominant amount of work also roughly doubles. The factor 3 affects actual speed and +2 matters on small inputs, but neither changes the growth class.

7n + 20→Θ(n)

Drop the constant multiplier and fixed additive term.

4n² + 8n + 3→Θ(n²)

The quadratic term eventually dominates the linear term.

n log n + 40n→Θ(n log n)

n log n grows faster than n.

The three main symbols

Θ

Tight growth class

T(n) = Θ(n) means the running time is bounded above and below by linear functions, up to constant factors.

O

Upper bound

T(n) = O(n²) can be true even for a linear algorithm, but it is a loose statement. Big O says the growth will not exceed that order asymptotically.

Ω

Lower bound

T(n) = Ω(n) means that for large n, the amount of work grows at least proportionally to n.

most informativeT(n) = Θ(n)
true but looseT(n) = O(n²)

For a linear scan, both statements can be mathematically true, but the first one tells us much more about the algorithm.

Formal definitions

Big O: T(n)=O(g(n)) if there are constants c>0 and n₀ such that 0≤T(n)≤c·g(n) for every n≥n₀.

Big Ω: T(n)=Ω(g(n)) if there are constants c>0 and n₀ such that 0≤c·g(n)≤T(n) for every n≥n₀.

Big Θ: T(n)=Θ(g(n)) when both asymptotic upper and lower bounds hold.

The second resource

Space complexity

Time is not the only cost. Algorithms may create temporary arrays, hash tables, queues, heaps, or recursion frames. We usually separate the input itself from additional working memory.

input array · Θ(n)
+
a few variables · Θ(1)
or
temporary array · Θ(n)

Auxiliary space

Memory used beyond the input. An in-place algorithm tries to keep this small, often Θ(1).

Recursion counts too

A recursion depth of d usually means Θ(d) stack frames even when no explicit arrays are created.

Time–space trade-off

Extra memory can save time: a hash table or memoization can prevent repeated work.

How to analyze a new algorithm

1

Define the input size

What exactly does n measure? Do you need a second parameter such as m?

2

Find repeated work

Look for loops, nested loops, recursive calls, repeated halving, and branching.

3

Choose the case

Are you analyzing the worst, average, or best case?

4

Simplify the growth

Keep the dominant term and state a tight Θ bound when you know it.

5

Check memory

Count temporary data structures and recursion depth, not only explicit arrays.

×

“O is the exact complexity.”

No. O is an upper bound and may be loose. Θ is usually used for a tight asymptotic class.

×

“Worst case and Big O are the same.”

No. Worst case defines a running-time function over inputs; O, Ω, and Θ describe asymptotic bounds on that function.

×

“Constants never matter.”

They matter in real implementations. Asymptotic analysis deliberately answers a different question: how performance scales.
