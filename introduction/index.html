Introduction to Algorithms

An algorithm is not just code that works. We also want to know how its work and memory grow when the input gets larger. This chapter builds that intuition first, then introduces the notation used to describe it precisely.

The central idea

Measure growth, not seconds

Wall-clock time is useful for benchmarking a program, but it depends on the computer, language, compiler, and current load. Algorithm analysis asks a more transferable question: how does the amount of work change when the input becomes larger?

Suppose we need to find a name in a list

If we scan from the beginning, a list twice as long can require about twice as many checks. The exact nanoseconds may change from laptop to laptop; the pattern “work grows proportionally to the list length” does not.

Step 3

Keep the growth pattern

Exact operation counts are often messy. Asymptotic notation keeps the part that controls growth for large n and discards machine-dependent constants and lower-order terms.

Suppose an algorithm uses

T(n) = 3n + 2
3 operations per element → 3n
2 setup operations
→
Θ(n)

Linear growth

If n doubles, the dominant work is roughly doubled. The “3” changes the speed; the “+2” matters for small inputs; neither changes the long-run growth class.

7n + 20→Θ(n)

Ignore the constant multiplier and fixed setup cost.

4n² + 8n + 3→Θ(n²)

The quadratic term eventually dominates the linear term.

n log n + 40n→Θ(n log n)

n log n grows faster than n.

Three symbols you will use most

Θ

Tight growth rate

T(n) = Θ(n) says linear growth describes the algorithm from both above and below, up to constant factors.

O

Upper bound

T(n) = O(n²) can be true for a linear algorithm, but it is loose. Big O answers “it grows no faster than this bound.”

Ω

Lower bound

T(n) = Ω(n) says the work eventually grows at least proportionally to n.

most informativeT(n) = Θ(n)
true but looseT(n) = O(n²)

For a linear scan, both statements can be mathematically true. The first tells us much more.

Formal definitions

Big O: T(n)=O(g(n)) if there are constants c>0 and n₀ such that 0≤T(n)≤c·g(n) for every n≥n₀.

Big Ω: T(n)=Ω(g(n)) if there are constants c>0 and n₀ such that 0≤c·g(n)≤T(n) for every n≥n₀.

Big Θ: T(n)=Θ(g(n)) when both an asymptotic upper and lower bound hold.

The second resource

Space complexity

Time is not the only cost. Algorithms may also allocate temporary arrays, hash tables, queues, heaps, or recursion frames. We usually distinguish the input itself from extra working memory.

input array · Θ(n)
+
a few variables · Θ(1)
or
temporary array · Θ(n)

Auxiliary space

Memory allocated in addition to the input. An in-place algorithm tries to keep this very small, often Θ(1).

Recursion counts too

A recursion depth of d usually means Θ(d) stack frames even if the code creates no explicit array.

Time–space trade-off

Extra memory can save time: a hash table or memoization cache may avoid repeated work.

A repeatable method

How to analyze a new algorithm

1

Define the input size

What exactly is n? Do you need a second parameter such as m?

2

Identify repeated work

Look for loops, nested loops, recursive calls, and repeated halving or branching.

3

Choose the case

Are you proving worst-case, average-case, or best-case behavior?

4

Simplify the growth

Keep the dominant term and state a tight Θ bound when you know one.

5

Check extra memory

Count temporary structures and recursion depth, not just explicit arrays.

×

“O means exact complexity.”

No. O is an upper bound and can be loose. Θ is the standard way to state a tight asymptotic growth rate.

×

“Worst case means Big O.”

No. Worst case specifies which running-time function we study; O, Ω, and Θ describe asymptotic bounds on that function.

×

“Constants never matter.”

They matter in real implementations. Asymptotic analysis intentionally answers a different question: how performance scales.
