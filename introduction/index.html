Chapter 1 · Foundations

Introduction to Algorithms

Before learning particular algorithms, we need a way to talk about their cost. The basic question is simple: when the input becomes larger, how much more work and memory does the algorithm need?

Throughout this chapter, n will usually denote the size of the input, T(n) the amount of work, and S(n) the extra memory used.

What do we actually measure?

Timing a program with a stopwatch is useful, but it mixes the algorithm with the machine, language, compiler, and implementation. Complexity analysis tries to separate those things.

This is the point of asymptotic analysis: we care less about whether one check takes three or five nanoseconds and more about how the number of checks changes with the size of the problem.

First decide what “input size” means

The symbol n has no universal meaning. It is only useful after we say what it counts.

Array or string
n is usually the number of elements or characters.
Graph
We often need two parameters: n=|V| vertices and m=|E| edges.
Matrix
The natural description may be n \times m, not a single number.
Integer
For arithmetic algorithms, the relevant size is often the number of bits used to write the integer.
Example. Saying that an algorithm is linear in the numeric value x is very different from saying that it is linear in the number of bits of x, which is about \log_2 x.

Count useful units of work

We normally use a simple RAM-style model: arithmetic on machine-sized values, comparisons, assignments, and array access are treated as constant-time operations.

total = 0
for x in a:
    total += x

One pass through an array

The loop performs a constant amount of work for every element. With n elements, the total work is proportional to n.

Worst-case analysis is common because it gives a guarantee without assuming how inputs are distributed. Average-case analysis can be more informative, but only after the distribution has been stated.

Asymptotic notation

Exact operation counts are often cluttered. Asymptotic notation keeps the part that matters when the input becomes large.

T(n) = 3n + 2
→
T(n) = Θ(n)

The coefficient 3 still matters in a real implementation, and the +2 matters for small inputs. But neither changes the fact that doubling n eventually doubles the dominant part of the work.

Θ(g(n))
A tight growth rate: the function is bounded above and below by constant multiples of g(n) for sufficiently large n.
O(g(n))
An asymptotic upper bound. It may be loose: a Θ(n) algorithm is also O(n²).
Ω(g(n))
An asymptotic lower bound.
Formal definitions

O. T(n)=O(g(n)) if there are constants c>0 and n_0 such that 0\le T(n)\le c g(n) for every n\ge n_0.

Ω. T(n)=Ω(g(n)) if 0\le c g(n)\le T(n) eventually.

Θ. Both bounds hold at the same time, possibly with different constants.

Space complexity

Time is only one resource. We also care about memory allocated while the algorithm runs.

An algorithm that scans an existing array with a few counters uses Θ(1) auxiliary space even though the input itself occupies Θ(n) memory. Recursion also counts: a recursion depth of d normally contributes Θ(d) stack frames.

Three examples to recognize

1

One scan

for x in a:
    total += x

Each element is visited once: Θ(n) time and Θ(1) extra space.

2

All unordered pairs

for i in range(n):
    for j in range(i + 1, n):
        check(a[i], a[j])

There are n(n-1)/2 pairs, so the running time is Θ(n²).

3

Repeated halving

while left <= right:
    mid = (left + right) // 2
    # discard half

After k steps the remaining range has size about n/2^k. Reaching one element takes Θ(log n) steps.

A useful habit. When reading code, first identify the size parameter, then the repeated work, and only then simplify the resulting expression.
