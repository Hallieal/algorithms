Кодирование Хаффмана

Частые символы должны иметь короткие коды. Хаффман добивается этого, каждый раз объединяя два узла с минимальными частотами.

Частые символы должны кодироваться дёшево

Если все символы кодируются одинаковым числом битов, частые и редкие символы стоят одинаково. Хаффман делает иначе: частые символы располагаются ближе к корню, редкие могут уйти глубже.

ПравилоОбъединяем два узла с минимальными частотами

Повторяем, пока не останется одно дерево.

Почему работаетРедкие символы можно сделать самыми глубокими соседями

После этого пара сжимается в одну меньшую задачу Хаффмана.

СложностьO(n log n)

Построить двоичный префиксный код, минимизирующий взвешенную длину ∑ fᵢ · ℓᵢ, где fᵢ — частота символа, а ℓᵢ — длина его кодового слова.

До дерева: сначала увидим, какие биты мы вообще экономим

Huffman становится гораздо понятнее, когда compression виден как задача подсчёта битов. Возьмём крошечное сообщение tilt: в нём всего три разных символа, причём один встречается дважды.

Фиксированное 8-битное представление

Четыре символа требуют 32 payload bits, если каждому символу отводить по 8 бит.

→

Frequency-aware code

Один допустимый Huffman code: t=1, i=00, l=01. Тогда tilt превращается в 1 00 01 1: всего 6 payload bits.

Что этот toy-example намеренно игнорирует

Реальный compressed file должен ещё хранить metadata, описывающую код, а современный текст обычно использует Unicode/UTF-8, а не один фиксированный 8-битный alphabet. Здесь изолируется главная идея: частым символам выгодно давать короткие codewords.

Попробуйте предсказать дерево

Какой символ должен оказаться ближе всего к root?

t встречается дважды, а i и l — по одному разу. Если path length равна code length, частый символ должен проходить меньше edges.

Префиксный код не требует разделителей

Если ни одно полное кодовое слово не является началом другого, декодер всегда понимает, где закончился символ. Именно это автоматически даёт двоичное префиксное дерево.

Не префиксный

При чтении 01... после первого бита непонятно, это уже A или начало B.

Префиксный

Каждое завершённое кодовое слово соответствует листу двоичного дерева, поэтому декодирование однозначно.

Variable-length code декодируется проходом по дереву, а не нарезкой на chunks

В fixed-width коде bit string можно разбить на одинаковые блоки. У Huffman длины различаются, поэтому decoder читает по одному bit, двигается по tree и выдаёт символ каждый раз, когда достигает leaf.

100011
Для t=1, i=00, l=01: читаем 1 → leaf t, возвращаемся в root; 00 → i; снова root; 01 → l; снова root; 1 → t. Никакие separators не нужны.
Tree одновременно задаёт код и границы символов. Prefix-free property означает: достигли leaf — текущий codeword точно закончен.

Объединяем два самых дешёвых поддерева

Берём две минимальные частоты, делаем их соседями, заменяем их суммой и повторяем. Каждое объединение означает, что эти два узла окажутся на один уровень глубже нового родителя.

1

Создаём лист для каждого символа

Вес листа равен частоте символа.

2

Извлекаем два минимума

Они станут соседними листьями на наибольшей глубине текущего дерева.

3

Объединяем

Создаём родителя с весом, равным сумме двух детей.

4

Возвращаем и повторяем

Продолжаем, пока не останется одно дерево.

Построим дерево по шагам

Оранжевым выделены два текущих минимума. Фиолетовым — только что объединённый узел.

Метки 0 и 1 условны

Если поменять местами левого и правого ребёнка любого внутреннего узла, сами битовые строки изменятся, но длины кодов останутся теми же. Поэтому оптимальных таблиц Хаффмана обычно много.

Та же greedy-структура: оптимальное слияние файлов

Правило Хаффмана «объединять два минимальных веса» работает не только для символов. Тот же priority-queue pattern минимизирует суммарную работу при последовательном слиянии файлов, если стоимость merge равна сумме размеров.

Плохой порядок

Размеры файлов: 4, 50, 5, 6. Если каждый раз объединять текущий результат со следующим в этом порядке, стоимости равны 54, затем 59, затем 65.

54 + 59 + 65 = 178

Сначала два минимальных

Объединяем 4+5=9, затем 6+9=15, затем 15+50=65.

9 + 15 + 65 = 89

Почему это Huffman под другим именем

Каждый раз после merge вес объекта снова оплачивается уровнем выше. Поэтому маленькие веса выгодно отправлять глубже в merge-tree. Для частот символов Huffman делает ровно это.

Насколько Хаффман близок к пределу энтропии?

Нормируем частоты до вероятностей pᵢ. Энтропия Шеннона H=-∑pᵢlog₂pᵢ — нижняя граница на среднюю длину любого двоичного префиксного кода, а для Хаффмана выполняется H ≤ L < H+1.

Энтропия H≈ 2.220 бит/символДля вероятностей 0.45, 0.13, 0.12, 0.16, 0.09, 0.05.
Средняя длина Хаффмана L2.24 бит/символ224 бита на 100 появлений символов.
Разрыв≈ 0.020 бит/символВ этом примере код почти достигает информационно-теоретической границы.

Худшая длина одного кода

При n символах отдельное кодовое слово Хаффмана может иметь длину до n−1 бит при достаточно перекошенных частотах. Оптимальная средняя длина не означает, что каждый символ кодируется коротко.

Почему два минимума можно сделать соседями

В доказательстве всего два хода. Сначала две минимальные частоты можно без ухудшения поместить в пару самых глубоких соседних листьев. Затем эту пару сжимаем в один псевдосимвол и решаем меньшую задачу.

1. Глубокие листья должны быть дешёвыми

Если символ с большей частотой находится глубже символа с меньшей частотой, обмен их меток не увеличивает стоимость. Поэтому маленькие частоты можно отправить на максимальную глубину.

2. Два минимума можно сделать соседями

Берём два самых глубоких соседних листа. Обменом меток можно добиться, чтобы именно две глобально минимальные частоты занимали эти позиции, не ухудшая стоимость.

3. Сжимаем пару

Заменяем листья с частотами x и y одним псевдосимволом частоты x+y. Оптимальное дерево для меньшей задачи после раскрытия пары даёт оптимальное дерево исходной задачи.

Оптимальная подструктура

После того как два минимальных символа зафиксированы как соседи, остаётся ровно ещё одна задача Хаффмана с меньшим числом узлов. Поэтому тот же жадный шаг можно повторять.

Interview recognition: меняющаяся коллекция + repeated min extraction → подумайте о heap

Huffman — чистый пример более общего priority-queue pattern. Candidate set меняется после каждого выбора, но на каждом шаге нужны только один-два highest-priority elements.

Repeated query

Какие два веса сейчас минимальны?

Ответ меняется после каждого merge, потому что combined node возвращается в candidate set.

Data structure

Min-heap

pop показывает current minimum, а push восстанавливает структуру после вставки merged weight. Полный re-sort не нужен.

Greedy rule

Merge, reinsert, repeat

Pattern почти буквально превращается в код: два pop, сложить веса, push суммы и продолжать, пока не останется одно tree.

Полезное обобщение

Если задача много раз спрашивает current min/max, пока candidate set изменяется, сначала думайте о priority queue, а не о «сортировать заново после каждого update».

Очевидная реализация Huffman получается квадратичной

Математическое rule говорит: «многократно извлекай два минимальных веса». Первая implementation-идея — каждый раз сканировать всю коллекцию, но именно repeated minimum search становится bottleneck.

Обычный list

Сканируем все текущие nodes, находим два минимальных, merge, возвращаем результат и повторяем. Примерно n merges × linear search дают O(n²).

Min-heap

Два минимальных веса всегда доступны наверху. Каждый pop или push стоит O(log n), поэтому все n−1 merges занимают O(n log n).

Почему heap естественен

Huffman не нужна полностью отсортированная коллекция после каждого merge. Нужен только повторяющийся доступ к одному-двум minimum elements. Heap поддерживает ровно столько порядка — и не вычисляет лишнего.

Весь алгоритм — это min-heap

Min-heap делает шаг «взять два минимума и вставить их сумму» эффективным. Счётчик нужен, чтобы Python не пытался сравнивать сами деревья при равных частотах.

Оптимальность внутри конкретной модели

Canonical Huffman codes в реальных форматах

Канонический код Хаффмана хранит длины кодовых слов, а сами битовые слова восстанавливает по детерминированному правилу. DEFLATE — формат, лежащий в основе gzip и zlib, — использует эту идею: достаточно передать длины, явное дерево не требуется.

Оптимум среди двоичных префиксных кодов

При заданных частотах символов Хаффман минимизирует ожидаемую или суммарную длину кода именно в этой модели.

Но это не «абсолютно лучшее сжатие»

Более сложные методы могут использовать блоки символов, контекст или вероятностную структуру, которой нет в простой модели независимых символов.

Задачи

1

Постройте код до конца

Для частот 2, 3, 7 и 8 выполните все объединения Хаффмана. Какова суммарная взвешенная длина и как она сравнивается с фиксированным 2-битным кодом?

Объединяем 2+3=5, затем 5+7=12, затем 8+12=20. Длины кодов: 1 для частоты 8, 2 для 7 и 3 для 2 и 3. Итого 8·1 + 7·2 + 2·3 + 3·3 = 37 бит. Фиксированный 2-битный код использовал бы 20·2 = 40 бит.
2

Префиксное свойство

Почему код одного листа двоичного дерева не может быть префиксом кода другого листа?

Тогда один лист должен был бы лежать на пути от корня к другому листу. Но у листа нет детей, поэтому это невозможно.
3

Взвешенная длина

Символ встречается 20 раз и получает код длины 3. Каков его вклад в общую длину?

20·3 = 60 бит.
