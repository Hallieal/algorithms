Huffman Coding

Frequent symbols should get short codes. Huffman achieves this by repeatedly merging the two least frequent nodes.

Frequent symbols should be cheap to encode

If every symbol uses the same number of bits, frequent and rare symbols cost the same. Huffman coding does better: common symbols move closer to the root, rare symbols are allowed to sit deeper.

Goal

Construct a binary prefix code minimizing the weighted code length ∑ fᵢ · ℓᵢ, where fᵢ is a symbol frequency and ℓᵢ is its codeword length.

Before the tree: see the bits you are trying to save

Huffman becomes much more intuitive once compression is visible as a bit-counting problem. Use a tiny message such as tilt: only three symbols appear, and one of them appears twice.

Fixed 8-bit character representation

Four characters use 32 payload bits if every character is stored with 8 bits.

→

Frequency-aware code

One valid Huffman code is t=1, i=00, l=01. Then tilt becomes 1 00 01 1: only 6 payload bits.

What this toy count ignores

A real compressed file must also communicate metadata such as the code description, and modern text is normally encoded with Unicode/UTF-8 rather than one fixed 8-bit alphabet. The example isolates the core idea: frequent symbols deserve shorter codewords.

Predict the tree

Which symbol should be closest to the root?

t appears twice, while i and l appear once each. If path length is code length, the frequent symbol should pay for fewer edges.

Prefix-free means no separators

If no codeword begins with another complete codeword, the decoder always knows when one symbol ends. That is exactly what a binary prefix tree guarantees.

Every completed codeword corresponds to a leaf of a binary tree, so decoding is immediate.

Variable-length codes are decoded by walking, not chunking

With fixed-width codes you can split the bit string into equal chunks. Huffman codewords have different lengths, so the decoder instead follows the tree one bit at a time and emits a symbol whenever it reaches a leaf.

100011
Using t=1, i=00, l=01: read 1 → leaf t, reset to root; read 00 → i; reset; read 01 → l; reset; read 1 → t. No separator symbols are needed.
The tree is both the encoder and the parser. Prefix-freeness means reaching a leaf tells the decoder exactly where the current symbol ends.

Merge the two cheapest subtrees

Take the two smallest frequencies, make them siblings, replace them by their sum, and repeat. Each merge says: these two nodes will be one level deeper than their new parent.

Swapping the left and right child of any internal node changes the literal bit strings but not any code length. Many different Huffman code tables are therefore equally optimal.

The same greedy structure: optimal file merging

Huffman’s “merge the two smallest weights” rule also solves the optimal merge pattern problem: repeatedly merging files costs the sum of their sizes, so early merge choices get paid again later.

Contiguous merge order

For file sizes {10,5,100,50,20,15}, repeatedly merge the current result with the next file. The merge costs are

15 + 115 + 165 + 185 + 200 = 680

Feasible—but far from optimal.

Two-smallest-first

Use a min-priority queue and repeatedly merge the two smallest current files:

15 + 30 + 50 + 100 + 200 = 395

The total work drops dramatically.

Why this is Huffman in disguise

Every leaf weight is paid once for each merge level above it. The total merge cost is therefore a weighted external path length—the same objective ∑wᵢ·depthᵢ minimized by a Huffman tree.

Same priority-queue skeleton, different story. Extract two minima → combine them → reinsert the sum → repeat.

How close is Huffman to the entropy limit?

Normalize the frequencies to probabilities pᵢ. Shannon entropy H=-∑pᵢlog₂pᵢ is a lower bound on the average length of any binary prefix code, while Huffman satisfies H ≤ L < H+1.

Worst-case depth

With n symbols, an individual Huffman codeword can be as long as n−1 bits for a sufficiently skewed frequency distribution. Optimal average length does not imply that every codeword is short.

Why the two smallest can be siblings

The proof needs only two moves. First, push the two smallest frequencies to a deepest sibling pair without increasing cost. Then contract that pair into one pseudo-symbol and solve the smaller problem.

1. Deep leaves should be cheap

In any optimal prefix tree, if a higher-frequency symbol is deeper than a lower-frequency symbol, swapping their labels cannot increase cost. Therefore small frequencies can be pushed to the greatest depths.

2. Two minima can be siblings

Take two deepest sibling leaves. By exchanging labels, we can arrange that the two globally smallest frequencies occupy those sibling positions without increasing total cost.

3. Contract the siblings

Replace the two leaves of frequencies x and y by one pseudo-symbol of frequency x+y. An optimal tree for this smaller instance expands back to an optimal tree for the original instance.

Optimal substructure

Once the two minimum-frequency symbols are committed as siblings, the remaining problem is exactly another Huffman problem on one fewer node. This justifies repeating the same greedy choice.

Interview recognition: a changing collection with repeated min extraction suggests a heap

Huffman is a clean example of a broader priority-queue pattern. The candidate set changes after every choice, but each step only needs the one or two highest-priority elements.

Repeated query

Which two weights are smallest now?

The answer changes after every merge because the combined node is inserted back into the candidate set.

Data structure

Min-heap

pop exposes the current minimum, and push restores the collection after inserting the merged weight. No global re-sort is necessary.

Greedy rule

Merge, reinsert, repeat

The algorithmic pattern becomes almost literal code: pop twice, add the weights, push the sum, and continue until one tree remains.

Generalization to remember

If the problem repeatedly asks for the current min/max while the candidate set changes, think priority queue before thinking “sort after every update”.

The obvious Huffman implementation is quadratic

The mathematical rule says “repeatedly remove the two smallest weights”. The first implementation idea is to scan the whole collection every time—but the repeated minimum search becomes the bottleneck.

Plain list

Find the two smallest nodes by scanning all current nodes, merge them, put the result back, and repeat. With roughly n merges and linear searches, this is O(n²).

Min-heap

The two smallest weights are always exposed at the top. Each pop or push costs O(log n), so all n−1 merges take O(n log n).

Why a heap is the natural structure

Huffman does not need the entire collection fully sorted after every merge. It only needs repeated access to the smallest one or two elements. A heap maintains exactly that amount of order—and no more.

The whole algorithm is a min-heap

A min-heap makes each “extract two minima and insert their sum” step efficient. A counter is included so Python never has to compare tree nodes when frequencies tie.

Optimal inside a specific model

Canonical Huffman codes in real formats

A canonical Huffman code stores the code lengths and reconstructs the actual bit patterns deterministically. DEFLATE—the format underlying gzip and zlib—uses this idea for its Huffman code descriptions: code lengths are enough to regenerate the codes, which avoids transmitting an explicit tree.

It is optimal among binary prefix codes

Given the symbol frequencies, Huffman minimizes expected or total codeword length within this model. Decoding needs no separators because symbols live only at leaves: reaching a leaf tells us exactly where one codeword ends.

It is not “the best possible compression” in every sense

More advanced methods can exploit blocks, context, or probabilities not represented by a simple independent-symbol prefix code.

Exercises

1

Build the whole code

For frequencies 2, 3, 7, and 8, perform all Huffman merges. What is the total weighted length, and how does it compare with a fixed 2-bit code?

Merge 2+3=5, then 5+7=12, then 8+12=20. The code lengths are 1 for frequency 8, 2 for 7, and 3 for 2 and 3, so the weighted length is 8·1 + 7·2 + 2·3 + 3·3 = 37 bits. A fixed 2-bit code would use 20·2 = 40 bits.
2

Prefix property

Why can no leaf codeword in a binary tree be a prefix of another leaf codeword?

A prefix would mean that one leaf lies on the root-to-leaf path to another symbol. But a leaf has no children, so that is impossible.
3

Weighted length

A symbol occurs 20 times and receives a codeword of length 3. How much does it contribute to the total encoded length?

20·3 = 60 bits.
