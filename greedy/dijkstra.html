Dijkstra’s Algorithm

Dijkstra's algorithm solves single-source shortest paths in graphs with nonnegative edge weights by finalizing vertices in increasing tentative-distance order.

Problem statement

Given a source vertex s in a graph with nonnegative edge weights, compute the minimum path cost from s to every reachable vertex.

RuleFinalize the smallest tentative distance

Then relax every outgoing edge from that vertex.

Why it worksNonnegative edges cannot create a cheaper path later

Once the minimum label is extracted, it is final.

CostO((V+E) log V)

Adjacency lists plus a binary heap.

Dijkstra’s setting

All edge weights must be nonnegative. The graph may be directed or undirected. Unreachable vertices simply keep distance ∞.

Shortest paths and MST are different objectives. Dijkstra minimizes each source-to-vertex path separately. An MST minimizes one global sum of selected edge weights.

Distances and predecessor information

A complete run of Dijkstra computes shortest-path distances from one source to all reachable vertices. Predecessor pointers can be stored at the same time to reconstruct actual paths.

Distance table

How cheap is each destination?

dist[v] stores the cheapest known source-to-v cost and becomes final when v is extracted safely.

Parent table

How do we actually get there?

parent[v] records the predecessor that produced the best cost. Backtracking parents reconstructs the route.

Visited/finalized

Which answers are settled?

This state separates tentative information from distances that the greedy proof says can never improve again.

Useful bonus. If you later ask for another destination from the same source, the distance information is already there; you do not need to rerun a single-target search from scratch.

Single-source and all-pairs queries

Dijkstra solves the single-source problem. If distances are required for every ordered pair of vertices, the outer problem is different and may call for repeated single-source runs or an all-pairs algorithm.

QuestionNatural approachImportant condition
One source → all verticesDijkstraAll edge weights are nonnegative
All sources → all verticesRun Dijkstra from each sourceStill requires nonnegative edge weights
All pairs with negative edgesUse an all-pairs method such as Floyd–WarshallFinite shortest paths require no relevant negative cycle
Do not confuse output scope with the greedy invariant. Repeating Dijkstra changes how many times we solve the problem; negative edges change whether its finalization proof is valid at all.

Reduction from vertex costs to edge costs

If costs are attached to vertices, assign each directed edge (u,v) the cost of its destination v. Dijkstra can then be used without changing the shortest-path routine.

Original model

Each vertex v has nonnegative cost c(v). The cost of a path is the sum of the costs of vertices visited.

Edge-weighted model

For every directed edge (u,v), assign weight w(u,v)=c(v). Traversing into v now pays exactly the cost that used to live on the vertex.

u → v   becomes   u ── c(v) ──→ v

One bookkeeping detail

If the path definition counts the source vertex’s own cost, add c(s) once to every final distance (or initialize dist[s]=c(s)). The edge transformation naturally charges every destination vertex but not the starting one.

Reduction is an algorithm-design skill. Before modifying a trusted algorithm, ask whether the new-looking problem can be translated into an old one while preserving the objective.

Finalizing tentative distances

Maintain the best known distance to every unfinished vertex. Repeatedly select the unfinished vertex with minimum tentative distance, finalize it, and relax its outgoing edges.

1

Start at the source

Set dist[s]=0 and all other distances to infinity.

2

Extract the minimum

Choose the unsettled vertex with the smallest current tentative distance.

3

Finalize it

Its tentative distance is now guaranteed to be the true shortest-path distance.

4

Relax outgoing edges

Try to improve each neighbor using a path through the newly finalized vertex.

Relaxation

For an edge (u,v) of weight w, replace dist[v] by min(dist[v], dist[u]+w).

Fewest edges versus minimum total weight

BFS minimizes the number of edges in an unweighted graph. Dijkstra minimizes the sum of nonnegative edge weights, so a shortest weighted path may contain more edges.

Two edges, total cost 11

S → X → T uses fewer segments. An unweighted BFS would prefer it because BFS measures distance in number of edges.

Three edges, total cost 7

S → A → B → T uses more segments but less total weight. Dijkstra prefers this path because the objective is accumulated cost.

Choose the algorithm from the meaning of distance. Fewest edges → BFS. Minimum sum of nonnegative weights → Dijkstra.

Edge weights as general nonnegative costs

The weights can represent distance, time, price, or any other additive nonnegative quantity. The algorithm only uses their order and additivity.

A trade graph

Imagine nodes are objects you can trade for and an edge weight is the extra money required for that trade. A path is then a sequence of trades, and its total weight is the money spent.

The same algorithm

The labels still mean “best cost found so far”. Relaxation asks whether reaching an item through the current node makes the total trade cheaper.

Key intuition

If the cheapest unfinished node costs 2, can a path that first reaches a node costing 6 later come back and beat 2?

Not when every remaining edge cost is nonnegative. You have already spent at least 6 before taking another edge. This is the everyday version of the correctness proof.

Algorithm steps

Each iteration performs four operations: extract the smallest tentative distance, finalize that vertex, relax its outgoing edges, and continue until no reachable unfinished vertex remains.

1. Pick

Choose the unfinalized vertex with the smallest tentative distance.

2. Finalize

Declare that distance permanent. Nonnegative edges are what make this commitment safe.

3. Relax

Try every outgoing edge and improve neighbors through the newly finalized vertex.

4. Repeat

The frontier moves outward in nondecreasing distance from the source.

new candidate distance to v = dist[u] + w(u,v)

Relation to breadth-first search

BFS and Dijkstra both expand vertices in nondecreasing distance from the source. BFS can use a FIFO queue because every edge has equal cost; Dijkstra needs a priority queue for unequal weights.

GraphFrontier structureWhy it works
Unweighted or all edges have equal weightFIFO queueVertices discovered one layer later are exactly one edge farther away.
Nonnegative weighted graphMin-priority queueThe next safe vertex is the one with smallest accumulated tentative cost, not the one discovered earliest.
Useful reduction. If every edge weight is 1, Dijkstra’s priority order collapses to BFS layers. Use BFS: it is simpler and runs in O(V+E).

Recover the path to D

Reverse that chain to obtain S → B → A → C → D. Distances answer “how cheap?”; parents answer “which path?”.

Why finalization is correct

Let u be the unfinished vertex with minimum tentative distance. Any alternative path to u must first enter the unfinished region at a vertex whose tentative distance is no smaller, so with nonnegative edges it cannot improve u.

1

Assume there is a shorter path from s to u than dist[u].

2

On that shortest path, let x be the first unsettled vertex and y its predecessor. Then y is already finalized.

3

When y was finalized, relaxing (y,x) made dist[x] no larger than the true path length from s to x.

4

Because all remaining edge weights are nonnegative, that prefix length is at most the full shortest-path length to u. Thus dist[x] ≤ δ(s,u).

5

But u has the minimum tentative distance, so dist[u] ≤ dist[x] ≤ δ(s,u). Since dist[u] is itself the length of some discovered path, it cannot be below δ(s,u). Therefore equality holds.

Where nonnegativity is used

The proof needs the length of a prefix of a shortest path to be no larger than the full path length. A negative edge later on the path can destroy exactly this inequality.

Why negative edges invalidate Dijkstra

A negative edge can create a cheaper path to a vertex after that vertex has already been finalized. This breaks the invariant used by the correctness proof.

What Dijkstra sees first

After processing S: dist[A]=2 and dist[B]=5. It finalizes A because 2 is smaller.

→

But the true shortest path

The path S→B→A has length 5−10 = −5, which is much shorter. The “final” value 2 was not actually safe.

Use Bellman–Ford or another appropriate method when negative edges are present. Dijkstra is correct with zero-weight edges, but not with negative ones.
A diagnostic red flag

If a vertex you already finalized later receives a cheaper distance, the greedy assumption has been violated.

That is exactly what a negative edge can cause. In a correct Dijkstra run, a finalized distance never needs to decrease.

Two nearby algorithms

Bellman–Ford repeatedly relaxes all edges and can handle negative weights (and detect reachable negative cycles). A* is a goal-directed relative of Dijkstra: it orders the search by distance-so-far plus an admissible heuristic. Neither has a standalone page in this handbook yet.

Array and heap implementations

The abstract operation is to extract the unfinished vertex with minimum tentative distance. A linear scan gives O(V²); a binary heap is preferable on sparse graphs.

Simple array / linear search

Finding the next minimum may scan all unvisited vertices. Repeating that can produce an O(V²) implementation. This version is often easier to trace by hand.

Min-priority queue

A heap exposes the next minimum efficiently. With adjacency lists, the standard heap implementation runs in O((V+E) log V), commonly written O(E log V) for connected graphs.

Same algorithmic proof, different engineering trade-off

The array version is pedagogically simple; the heap version better matches the repeated “give me the cheapest frontier vertex” operation. Complexity belongs to the implementation, not just the algorithm’s name.

Priority-queue implementation

Python's heapq does not provide decrease-key. Push a new pair whenever a distance improves and ignore stale entries when they are later removed.

1import heapq
2
3def dijkstra(graph, source):
4 dist = [float("inf")] * len(graph)
5 dist[source] = 0
6 heap = [(0, source)]
7
8 while heap:
9 d, u = heapq.heappop(heap)
10 if d != dist[u]:
11 continue
12 for v, w in graph[u]:
13 new_dist = d + w
14 if new_dist < dist[v]:
15 dist[v] = new_dist
16 heapq.heappush(heap, (new_dist, v))
17
18 return dist

Important lines

9–11

Ignore stale heap entries whose stored distance is no longer current.

12–16

Relax every outgoing edge. If a shorter path is found, update the label and push the new pair into the heap.

Lazy heap vs indexed priority queue

The implementation above pushes a fresh entry whenever a distance improves and ignores stale copies later. It is short and idiomatic Python, but the heap can grow to O(E). An indexed priority queue with a true decrease_key keeps one heap entry per vertex—O(V) heap space—but needs a more complicated data structure.

Path reconstruction

Store parent[v] whenever dist[v] improves. Following parent pointers backward from a destination reconstructs a shortest path.

1if new_dist < dist[v]:
2 dist[v] = new_dist
3 parent[v] = u
4 heapq.heappush(heap, (new_dist, v))

Every improvement records the route

If going through u makes v cheaper, then u becomes the predecessor of v on the best path currently known.

Target

Start from the destination and read its parent.

Backtrack

Follow parent[target], then the parent of that vertex, and so on until the source.

Reverse

The parent chain is stored backward, so reverse it to obtain the source-to-target path.

Two outputs, two data structures. dist answers “how much?”, while parent answers “which sequence of choices?”.

Same control flow, different invariant

Both algorithms can look like “pop a minimum, inspect neighbors, push updates”. Prim measures the price of attaching a vertex to a tree. Dijkstra measures the full price of reaching that vertex from the source.

Modeling shortest-path problems

Translate the application into vertices, edges, edge weights, and weight restrictions before selecting the shortest-path algorithm.

1

Vertices

What are the states? Cities, pages, accounts, configurations, positions, or something else?

2

Edges

What single transition is allowed from one state to another? Is direction important?

3

Weights

What accumulates along a path—distance, time, price, risk, or another additive cost?

4

Weight restriction

If every edge weight is nonnegative, greedy finalization is plausible. Negative edges are the immediate warning sign against Dijkstra.

Unweighted

Think BFS first

If every move has equal cost, level-order traversal already processes states in nondecreasing distance.

Weighted ≥ 0

Think min-priority queue

The repeated operation is “give me the unfinalized state with minimum tentative cost”. This is the heap pattern.

Negative edge

Stop and change methods

The local finalization step can become invalid because a cheaper route may arrive later through a negative contribution.

What to say before implementation

“I have a single-source shortest-path problem with additive nonnegative edge weights, so I can safely finalize the smallest tentative distance and use a min-heap to expose that vertex efficiently.”

Exercises

1

Relaxation

If dist[u]=7, edge (u,v) has weight 4, and dist[v]=15, what happens?

The path through u has length 7+4=11, so dist[v] improves from 15 to 11.
2

Zero edge

Does an edge of weight 0 invalidate Dijkstra’s correctness?

No. The proof requires nonnegative weights, and zero is nonnegative.
3

Unreachable vertex

What distance does Dijkstra return for a vertex that cannot be reached from the source?

Its distance remains infinity.
4

Why skip stale entries?

Why can the heap contain several entries for the same vertex? In the worst case, how large can the lazy heap become?

Each successful relaxation pushes a new pair because heapq has no decrease-key. Older pairs remain and are ignored when popped. There can be O(E) successful improvements/pushes, so the lazy heap may contain O(E) entries; this is why the precise bound for this implementation is O((V+E) log E).
