Key idea

A good algorithm often pays once to create structure, then exploits that structure many times.

A local strategy

Insertion sort

Keep a sorted prefix. Take the next element and insert it where it belongs.

The invariant

Before iteration \(i\), the prefix \(a[0:i]\) is sorted. The iteration extends that prefix by one element.

sorted prefix
136487
The current key is 4. Shift larger elements right, then insert.

Why it works

Initialization. A one-element prefix is sorted.

Maintenance. We insert the next key into its unique correct position inside the sorted prefix.

Termination. When the prefix has length \(n\), the whole array is sorted.

Press Next step.
def insertion_sort(a):
    for i in range(1, len(a)):
        key = a[i]
        j = i - 1
        while j >= 0 and a[j] > key:
            a[j + 1] = a[j]
            j -= 1
        a[j + 1] = key
    return a

Read the code as an argument

Line 2. Position 0 is already a sorted prefix of length one.

Lines 3–4. Save the next key and start immediately to its left.

Lines 5–7. Every larger value must move one position right.

Line 8. The first non-larger value marks the insertion point.

best\(O(n)\)already sorted
average\(O(n^2)\)many shifts
worst\(O(n^2)\)reverse order
memory\(O(1)\)in-place
Divide and conquer

Merge sort

Split until the pieces are trivial. Then merge sorted pieces back together.

8 3 6 2 7 1 5 4
↙        ↘
8 3 6 27 1 5 4
↙ ↘      ↙ ↘
8 36 27 15 4
split until one element · merge in sorted order
1 2 3 4 5 6 7 8

Where does \(n\log n\) come from?

Each level processes all \(n\) elements during merging. Every split halves the problem, so there are \(\log_2 n\) levels.

\[T(n)=2T(n/2)+\Theta(n)=\Theta(n\log n).\]

Merge is the whole trick

If two arrays are already sorted, compare only their first unused elements. The smaller one must be the next element of the merged result.

Each pointer moves forward at most once per element, so merging is linear.

Follow the merge operations

Press Next step.
def merge_sort(a):
    if len(a) <= 1:
        return a

    mid = len(a) // 2
    left = merge_sort(a[:mid])
    right = merge_sort(a[mid:])

    return merge(left, right)

What the recursion promises

The recursive calls return two sorted halves. Once that promise is granted, the only remaining work is a linear merge.

The base case is not merely a programming detail: arrays of length 0 or 1 are already sorted.

best\(O(n\log n)\)same recursion tree
average\(O(n\log n)\)guaranteed
worst\(O(n\log n)\)guaranteed
memory\(O(n)\)typical array version

Quicksort

Choose a pivot. Put smaller elements on one side and larger elements on the other. Recurse.

The catch

Quicksort is fast when partitions are reasonably balanced. Repeatedly choosing a terrible pivot can create \(n-1\) and \(0\) sized subproblems and lead to \(O(n^2)\).

Try it

Watch the pivot find its place

Press Next step.
def quicksort(a):
    if len(a) <= 1:
        return a

    pivot = a[len(a) // 2]
    left = [x for x in a if x < pivot]
    equal = [x for x in a if x == pivot]
    right = [x for x in a if x > pivot]

    return quicksort(left) + equal + quicksort(right)

A clear version before an in-place version

This implementation uses extra arrays so that the partition idea is visible. Production implementations usually partition in place.

Randomized pivot selection makes persistent worst-case partitions extremely unlikely.

best\(O(n\log n)\)balanced pivots
average\(O(n\log n)\)typical
worst\(O(n^2)\)bad pivots
memory\(O(\log n)\)in-place, expected stack

Algorithmic thinking

Why can insertion sort still be useful?

It has quadratic worst-case complexity. Why would a serious sorting implementation ever use it?

For tiny arrays, constant factors dominate asymptotics. Insertion sort has very low overhead, excellent cache behavior, and is especially fast on nearly sorted data. Hybrid sorts often switch to it for small subarrays.
A limit on all comparison sorts

Why \(O(n\log n)\) is fundamental

If an algorithm learns only by comparing pairs of elements, every comparison gives one binary answer.

\(a_1 < a_2?\)
↙ yes no ↘
next comparison
next comparison
⋮            ⋮
at least \(n!\) leaves

A correct algorithm must distinguish all \(n!\) possible input orders. A binary decision tree of height \(h\) has at most \(2^h\) leaves, hence

\[2^h \ge n! \quad\Longrightarrow\quad h \ge \log_2(n!) = \Omega(n\log n).\]
Conclusion

No comparison-based sorting algorithm can have worst-case complexity \(o(n\log n)\) for arbitrary distinct inputs.

Escape the lower bound

Can sorting be linear?

Yes — if we use more information than pairwise comparisons.

Counting sort

If every key is an integer in a small range \(0,\dots,k\), count how many times each key appears.

input2 0 3 2 1 0 2
counts0→2 · 1→1 · 2→3 · 3→1
output0 0 1 2 2 2 3

Complexity

Reading the array costs \(O(n)\). Traversing the count array costs \(O(k)\).

\[O(n+k)\]

This does not contradict the comparison lower bound: counting sort does not operate only through comparisons.

Practice

Think before you code

1

Nearly sorted

An array is already sorted except that one element was moved to another position. Which of the three algorithms above would you expect to perform especially well, and why?

Insertion sort. Only a limited number of shifts may be needed, while its scan through the array remains linear. Its running time adapts to how far the input is from sorted order.
2

Stable sorting

You have students sorted by name and now sort them by grade. How can stability preserve useful information from the first ordering?

With a stable sort by grade, students with the same grade remain ordered by name. Stability lets a previous ordering survive inside ties.
3

Bad pivots

Suppose quicksort always chooses the first element as pivot. Give a simple family of inputs producing worst-case behavior.

Already sorted arrays, or reverse-sorted arrays. The pivot is always an extreme element, so the partition sizes are 0 and \(n-1\) at every recursive step.
