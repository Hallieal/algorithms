Designing Dynamic Programs

Dynamic programming is easier to reason about as a method for building a small acyclic graph of subproblems and evaluating each vertex once, rather than as a collection of special formulas.

When should you try DP?

DP is especially natural when a solution can be assembled from smaller solutions and different lines of reasoning repeatedly reach the same subproblems. Words such as minimum, maximum, number of ways, and possible/impossible often occur in these problems, but they are clues rather than proofs.

Overlapping subproblems

Different branches of the computation reach the same state.

Sufficient state

The future depends on the state, not on the complete history used to reach it.

A state should contain exactly the information the future needs

A state is all information about the past that can affect future decisions. Two histories may be merged into one DP subproblem only when, after reducing them to the same state, the remaining problem is genuinely identical for both.

A good state should not remember how we arrived if that history no longer affects the legal future decisions.

Derive the recurrence from the final decision

A useful way to derive a transition is to ask how an optimal solution can end. A grid path enters its final cell from above or the left; the last knapsack item is taken or skipped; the final characters of two prefixes are matched or one is discarded. Once the final choice is fixed, what remains should be a smaller problem of the same kind.

Dependencies determine evaluation order

A recurrence defines directed dependencies between states. Bottom-up evaluation must process a state only after every state it depends on. In one-dimensional DP this is often index order; on a grid it is a row/column order. Sometimes no obvious order exists, which is a reason to inspect the state graph more carefully.

evaluate the dependency graph in a topological order

Memoization obtains a valid order through recursive calls: a state finishes after its dependencies. Tabulation makes the order explicit in loops. This is why top-down is often convenient for validating a recurrence, while bottom-up gives more control over order and memory.

Count states, not loops

Once the state is defined, complexity often becomes immediate: multiply the number of distinct states by the work needed to process one state. This is more reliable than counting nested loops in code that has already been written.

time ≈ number of reachable states × work per state

Not every recursion becomes a useful DP

A recursive formulation does not guarantee that DP will help. If almost every call has a unique state, memoization saves little. If the state must preserve nearly the entire decision history, the state space may remain exponential. And if transitions form cycles with no valid evaluation order, the problem may require a different formulation or a different algorithm.

DP helps

Few distinct recurring states; history can be summarized compactly; dependencies admit a useful order.

Be careful

Exponentially many states; the future depends on full history; the state graph contains problematic cyclic dependencies.

A working checklist

1
Subproblem

What exactly does the answer for one state mean?

2
State

Which parameters completely determine the remaining problem?

3
Transition

What can the final choice or final move be?

4
Base cases

Which states have an immediate answer?

5
Order

Are all dependencies available before a state is evaluated?

6
Answer

Which state contains the answer to the original problem?

7
Complexity

How many states are there, and how much work per state?

8
Reconstruction

Do we need only the value or the solution itself?

If these eight questions have precise answers, implementation is usually mechanical. Most of the intellectual work in DP happens before the loops are written: choosing the subproblems and justifying the transition.
