Introduction to Dynamic Programming

Dynamic programming does not begin with a table. It begins with a question: which subproblems are we solving again and again?

Start with ordinary recursion

Consider the Fibonacci numbers. Their definition turns almost word for word into a recursive function: to find F(n), find F(n−1) and F(n−2). The code is short and correct. The problem is how often it repeats the same work.

Python
def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

Calling fib(5) starts fib(4) and fib(3). But fib(4) itself asks for fib(3) again. Then fib(2) is recomputed several times. As n grows, this duplication spreads through the recursion tree.

Where the time goes

A central sign of DP is a small set of distinct subproblems that an ordinary recursive solution visits many times.

Store each answer once

Instead of recomputing a known F(k), store the result the first time it is found. Then each k from 0 through n is handled once. The branching recursion tree collapses into a sequence of stored values.

F(n) = F(n − 1) + F(n − 2)

This is the recurrence, or transition: it tells us which smaller states determine the current one.

State and transition

A state is the smallest information that uniquely identifies a subproblem. Fibonacci needs only n, so we can write the state as dp[n]. A grid problem may need (row, col). Knapsack often needs both the item index and the remaining capacity.

State

What smaller problem does dp[i], dp[i][j], or another state actually mean?

Transition

How is the answer for this state expressed using smaller states already defined?

If the meaning of a state is vague, the recurrence usually becomes guesswork too. In later sections we will define each state in words before writing code.

Building a DP solution

1

Define the subproblem: what exactly should one dp entry store?

2

Choose the state: what information distinguishes one subproblem from another?

3

Write the transition: which smaller states can lead to the current one?

4

Set the base cases and a valid evaluation order.

5

If the actual solution is needed, store enough information to reconstruct the choices.

This order matters more than syntax. Memoization and tabulation are two ways to evaluate the same system of states and transitions.

When to look for dynamic programming

SignWhat to look for
Repeated subproblemsThe same recursive arguments appear again.
Built from smaller answersA state's answer can be expressed through a few smaller states.
Sequence of decisionsEach step offers a small set of choices: take/skip, arrive from above/left, match/skip.
Optimize or countMinimum, maximum, number of ways, reachability, or best cost.

No single sign proves that a problem requires DP. Together, however, they suggest trying to define a state and a recurrence.
