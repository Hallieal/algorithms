Reconstructing a Solution

A DP table often stores only the optimum value. If the problem asks for the chosen items, a path, or an operation sequence, we must recover the decisions that led to the final state.

An optimal value is not an optimal solution

An LCS table may tell us that the maximum length is 3; a knapsack table may report a maximum value of 12. Those numbers alone do not identify the chosen characters or items. During DP we already compared legal predecessor states. Reconstruction simply follows those decisions in reverse.

Value

Maximum value = 12. LCS length = 3. Minimum cost = 7.

Solution

Items {0, 3}. Subsequence “ABD”. A particular path through the grid.

Walk backward through transitions

Start at the final state. Determine which transition could have produced its value, move to that predecessor, and repeat until a base state is reached. This is why reconstruction normally proceeds from the answer back toward the beginning.

Example: which knapsack items were chosen?

For 0/1 knapsack, compare dp[i][w] with dp[i−1][w]. If they are equal, there is an optimal solution that skips item i. If they differ, the current item was taken: record it and reduce the remaining capacity by its weight.

dp[i][w] = dp[i−1][w]   ⇒   item i may be skipped
dp[i][w] ≠ dp[i−1][w]   ⇒   item i is chosen
Python · value + chosen item indices
def chosen_items(weights, values, capacity):
    n = len(weights)
    dp = [[0] * (capacity + 1) for _ in range(n + 1)]

    for i in range(1, n + 1):
        weight = weights[i - 1]
        value = values[i - 1]

        for w in range(capacity + 1):
            dp[i][w] = dp[i - 1][w]
            if weight <= w:
                dp[i][w] = max(
                    dp[i][w],
                    value + dp[i - 1][w - weight]
                )

    chosen = []
    w = capacity

    for i in range(n, 0, -1):
        if dp[i][w] != dp[i - 1][w]:
            chosen.append(i - 1)
            w -= weights[i - 1]

    chosen.reverse()
    return dp[n][capacity], chosen

When to store parent pointers

Sometimes the table values make the predecessor easy to infer, as in standard LCS or knapsack. With more complicated transitions it is often cleaner to store an explicit predecessor — a parent pointer — while computing each state. The numeric table answers “how good?”, while the parent answers “where did this state come from?”.

General pattern
parent[r][c] = previous_state

# After the DP table is complete:
state = goal
path = []

while state is not None:
    path.append(state)
    state = parent[state]

path.reverse()

What if several optimal solutions exist?

The optimum need not be unique. If two transitions produce the same value, an ordinary traceback returns one solution according to its tie-breaking rule. Enumerating every optimal solution requires following every optimal branch, and the number of such solutions can be very large.

Tie-breaking does not change the optimum value, but it can change the particular solution returned. Thus a condition such as >= instead of > may affect reconstruction even when the numeric DP is unchanged.

Space compression can erase the path

Memory optimization and solution reconstruction serve different goals. If we keep only two rows or a few scalars, old decisions may disappear. Sometimes extra metadata is enough; sometimes the full table must be retained; for some problems more sophisticated low-memory reconstruction methods are possible.

Stored dataOptimum valueEasy reconstruction
Full DP table✓✓
Full table + parents✓✓ explicit
Only recent rows✓usually no
A few scalars✓usually no

That is why “do we need only the value, or the solution itself?” should be answered before applying memory compression, not afterward.
